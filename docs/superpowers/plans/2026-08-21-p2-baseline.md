# P2 lighting & atmosphere — pre-change baseline

Recorded before any lighting/post-processing work (ACES tone mapping, bloom, distance fog)
lands, using the shared in-browser harness from `task-1-brief.md`. Every later task in this
plan compares its "after" measurements against the numbers here.

## Environment used

- Dev server via `preview_start` (`dev` config), Vite on `http://localhost:5173`.
- Driven as a dispatched subagent through the `mcp__Claude_Browser__*` MCP tools
  (navigate, computer, javascript_tool, read_page, get_page_text).
- Intro AVG dialogue cleared (SKIP → picked the left branch → SKIP) until
  `document.body.innerText.trim()` was empty, confirming no overlay sits over the canvas.
- `window.hub` / `window.charController` dev handles present as expected.

## Environment limitations discovered (read before comparing later tasks against this file)

Two things in the Step 2 harness, taken exactly as written in the brief, do not do what
their comments claim on this build. Both are console-side workarounds — nothing under
`src/` was touched.

1. **The Browser pane never composites for this dispatched subagent.** `document.hidden`
   reads `true` for the entire session, before and after fronting the tab
   (`tabs_select`) and after `resize_window`. Every `computer` `screenshot` and `zoom`
   call timed out with: *"Screenshot timed out after 5s: the Browser pane is not
   displayed, so the page is not compositing frames. Display the pane and retry."* There
   is no tool available to this agent to make the pane visible/compositing. **No
   screenshots could be captured for this task** — the RGB pixel samples below (read
   directly from the WebGL back buffer via `gl.readPixels`, which does not require
   compositing) are the only visual record.
2. **`window.__fps()` cannot produce a live number while the pane is hidden.**
   `requestAnimationFrame` is fully frozen while `document.hidden` is `true`:
   `engine.frameId` did not advance at all (`134` → `134`) across a 3-second window with
   `engine.runRenderLoop()` active. `engine.getFps()` returns a stale, cached value left
   over from before the tab went hidden (`58.559...`, rounds to `59`), not a real
   measurement. The `fps` figure recorded below is that frozen value — **treat it as
   informational only, not evidence of real frame cost**, and expect the exact same
   frozen number in later tasks' `__fps()` calls regardless of what post-processing is
   added. `drawCalls` and `activeMeshes` are ordinary state snapshots (not time-based), so
   those two are real.
3. **The brief's literal `__view()` does not hold the camera still.** `followCamera.ts`
   registers a `scene.onBeforeRenderObservable` callback that recomputes
   `camera.position` / `camera.setTarget()` from the player every `scene.render()` call —
   including manual ones; `engine.stopRenderLoop()` only halts the automatic rAF loop, not
   this observable. So the brief's plain `cam.position.set(...)` before the final render
   was being silently overwritten before the draw (confirmed: after running the harness
   verbatim, the camera ended up at the default follow offset, `(≈0, 1.9, 4.9)`, not at any
   of the three specified eye positions, and all four sample points read the scene's flat
   clear color `(51, 51, 77)` — i.e. nothing had actually been drawn at the intended
   camera pose). **Fix applied in-session** (console only, matches the brief's own stated
   intent — "the follow camera cannot move the shot"): `__view()` now adds a temporary
   `onBeforeRenderObservable` observer that reasserts the eye/look *after* the follow
   camera's own observer runs in the same frame (Babylon notifies observers in
   registration order, so an observer added later runs after one added at camera
   creation), then removes itself immediately. `__place`, `__sample`, and `__fps` are
   unmodified from the brief. With the fix, `follow.camera.position` matched the requested
   eye position exactly for all three viewpoints (verified below).
4. The canvas's WebGL drawing buffer is `300×150` (the HTML default), not resized to its
   `800×450` CSS layout size — the resize presumably never fires while the tab is hidden.
   Sampling still works (`__sample`'s fractional coordinates scale to whatever buffer size
   is current), but later tasks should expect the same small buffer, not `800×450`.

None of this blocked collecting real data — the RGB samples below are genuine rendered
pixels from the three requested camera poses, read straight from the GPU back buffer.

Notes on reading these:
- `spawn`'s "sky" sample fraction (top of frame) lands in dark green — at this eye
  position (close to the player, looking mostly at their surroundings) the top of the
  frame is foliage/canopy, not open sky. Same story for `shade`'s sky sample (27, 47, 20)
  — that viewpoint looks into shaded terrain, not the horizon.
- `mountains` is the one viewpoint whose "sky" sample fraction is genuinely open sky:
  (152, 194, 234), a pale blue — this is the most useful row for judging tone-mapping/fog
  changes to the actual sky.
- These are absolute pixel values; later tasks should diff against these same four points
  at the same three camera poses.
